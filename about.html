架構與設計思路

系統分成「讀」和「寫」兩條獨立路徑：讀路徑要快 (毫秒級回傳推薦)，寫路徑要穩 (任何時候都不能掉評分、還要順手把每筆評分餵給監控)。兩條路徑中間放了一個 Kafka 訊息佇列當緩衝信箱 ─ Flask 收到評分後只要丟進信箱就回應使用者，後面 Spark、HBase、監控各自從信箱拿走慢慢處理，誰塞車都不會拖到 Flask，模型重訓也不用停服務

整體資料流

[ 瀏覽器 ] │ ├── 看推薦：GET /recommend?user_id=1 ──┐ │ ▼ │ [ Flask ] │ │ │ ▼ │ [ HBase recommendations ] ◄── 由 Spark MLlib ALS │ │ 每週離線批次預先算好 │ ▼ │ 回傳 Top-20 (HTML/JSON) │ └── 評分：POST /rate ──┐ ▼ [ Flask ] │ ▼ [ Kafka topic: user-ratings ] │ ▼ [ Spark Streaming on YARN ] ← 每 5 秒一個微批次 │ ┌─────────────┼─────────────┬──────────────────┐ ▼ ▼ ▼ ▼ [ HBase [ NCF [ HDFS [ /monitor user_ratings ] Scorer ] Parquet ] 儀表板 ] 下次重訓的 即時算誤差 給 Trino 跑 即時更新 訓練資料 (MAE/RMSE) SQL 分析 MAE/RMSE/PSI

NCF 線下 RMSE 比 ALS 低約 6%，但線下贏不等於上線贏 ─ 真正要全切過去得 A/B Test 看點擊率、留存才算數。所以兩個模型都留著，分工是：ALS 預先算好寫進 HBase 撐毫秒級流量，NCF 即時推理做重排序與線上比對

自架在 5 台 VM 叢集上 (master + 3 workers + admin)。因為這個頁面是從 admin VM 的 Flask serve 出來的，而 Flask 啟動時要連 HBase Thrift、載入 NCF 模型 checkpoint、抓 HDFS 上的 movies.csv，所以你能正常看到這頁，代表整條鏈路 (HDFS / HBase / Flask / 模型) 都還活著
