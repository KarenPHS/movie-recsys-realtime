架構與設計思路

系統分成「讀」和「寫」兩條路徑：讀路徑要快 (毫秒級回傳推薦)，寫路徑要穩 (任何時候都不能掉評分)。使用者評分後，Flask 只負責把事件寫入 Kafka 訊息佇列並即時回應，前後端各自獨立、互不阻塞；佇列把事件存於磁碟、依序排隊，具備削峰填谷的緩衝能力 ─ 尖峰暫存、離峰消化，不掉資料也不拖慢服務。評分進來後走兩條路：① 存進 Kafka 累積，當作模型批次重訓的資料；② 由服務內的 ModelScorer 當場算預測誤差，即時更新 /monitor 的 MAE/RMSE/PSI。

整體資料流

[ 瀏覽器 ] │ ├── 看推薦：GET /recommend?user_id=1 ──┐ │ ▼ │ [ Flask ] │ │ │ ▼ │ [ HBase recommendations ] ◄── 由 Spark MLlib ALS │ │ 每週離線批次預先算好 │ ▼ │ 回傳 Top-20 (HTML/JSON) │ └── 評分：POST /rate ──┐ ▼ [ Flask ] ┌─────────────┴──────────────┐ ▼ ▼ [ Kafka: user-ratings ] [ ModelScorer (服務內) ] 存著，當批次重訓 同一筆評分當場算 的訓練資料 預測誤差 (MAE/RMSE) │ + PSI 追蹤分佈漂移 ▼ [ /monitor 儀表板 ] 即時更新 MAE/RMSE/PSI

說明：ALS 離線批次把推薦預先算好寫進 HBase，查詢毫秒級、撐流量；評分事件丟進 Kafka 存著，作為下次批次重訓的資料；上線品質則由服務內的 ModelScorer 當場計算，不需另跑串流程式。

NCF 線下 RMSE 比 ALS 低約 6%，但線下贏不等於上線贏 ─ 真正要全切過去得 A/B Test 看點擊率、留存才算數。所以兩個模型都留著，分工是：ALS 預先算好寫進 HBase 撐毫秒級流量，NCF 即時推理做重排序與線上比對

自架在 5 台 VM 叢集上 (master + 3 workers + admin)。因為這個頁面是從 admin VM 的 Flask serve 出來的，而 Flask 啟動時要連 HBase Thrift、載入 NCF 模型 checkpoint、抓 HDFS 上的 movies.csv，所以你能正常看到這頁，代表整條鏈路 (HDFS / HBase / Flask / 模型) 都還活著
